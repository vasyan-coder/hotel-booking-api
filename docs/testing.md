# Проверки по требованиям

Все модульные и интеграционные тесты выполняются командой `./mvnw verify`. Бизнес-тесты используют отдельные H2; HTTP-клиент проверяется локальным сервером без внешней сети. Сквозной сценарий запускается после `./scripts/start.sh` командой `python3 scripts/smoke.py`.

| Требование | Реализация | Проверка |
|---|---|---|
| Равномерность и конкурентность | `SchedulingService`, блокировка отеля, сортировка `timesBooked,id` | HotelIntegrationTest: параллельные выделения, повторные доставки, серия из 30 размещений; smoke: 12 конкурирующих запросов |
| Сага и компенсация | `BookingService`, `BookingTransactions`, `BookingRecovery` | BookingIntegrationTest: успех, конфликт, отмена во время выделения, отложенная компенсация, зависший PENDING |
| Retry/Timeout/CircuitBreaker | `RestHotelClient` | RestHotelClientTest: ограниченные повторы, тайм-аут, 409 без повторов, отдельный circuit компенсации |
| CRUD бронирований | BookingController, проверка владельца, пагинация | Создание/чтение/отмена, чужая запись, повтор ключа, изменение payload, неверные даты |
| Отели и номера | HotelController, RoomController, CatalogService | CRUD, уникальность номера в отеле, история запрещает удаление, фильтры и сортировки |
| Аналитика | `StatisticsService` | Обрезка интервалов границами отчёта, доля занятых ночей, исключение отмен |
| Gateway и Eureka | Discovery Server, `lb://` маршруты | WebTestClient: HTTP-маршрутизация, JWT forwarding; smoke: фактическое обнаружение работающих сервисов |
| JWT и роли | Resource Server + `@PreAuthorize` | Проверка подписи/issuer/audience/срока, 401/403, запрет внутренних маршрутов |
| Схема данных | Раздельные H2, JPA-ограничения и индексы | Реальные транзакции H2, уникальность requestId и room number; [схема](database.md) |
| Предзаполнение | Два отеля, пять номеров, два пользователя | Разная вместимость/цена, неработающий номер, ADMIN/USER; smoke создаёт собственный изолированный каталог |
| Структура кода | Controller → Service → Repository, HotelClient interface | Сетевые вызовы вне локальных транзакций, отдельный класс транзакционных операций |
| Стиль | Spotless + Google Java Format | `verify` останавливается при нарушении форматирования |
| Ошибки | ErrorDTO, advice и security handlers | 400/401/403/404/409/503 и корреляция в ответах |
| Логи | JSON, X-Trace-Id, bookingId | Gateway HTTP-тесты и smoke проверяют заголовок; клиентский тест проверяет передачу traceId |
| Документация | README модулей, OpenAPI, ADR | Примеры запуска и REST, архитектурная и ER-схема, описание ограничений |

## Границы проверки

Параллельные тесты проверяют корректность на ограниченном числе одновременных запросов, а не заявляют конкретную промышленную пропускную способность. Сериализация операций одного отеля выбрана сознательно. Масштабирование требует нагрузочного профиля, постоянной БД и метрик задержек; H2 in-memory используется согласно требованиям.

Тесты состояния саги используют управляемую реализацию HotelClient, а тесты HTTP-устойчивости — настоящий локальный HTTP-сервер. Smoke дополняет их связкой всех четырёх приложений.

`python3 scripts/fault-smoke.py` дополняет проверки сценарием с настоящими БД двух сервисов и HTTP-прокси: фиксация в Hotel до потери ответа, исчерпание повторов, недоступная компенсация, фоновое восстановление после снятия сбоя и запрет позднего повторного выделения.

Перед созданием тестовых данных smoke проверяет оба пути обнаружения сервисов: Gateway → Hotel и Gateway → Booking → Hotel. Ожидание ограничено и повторяет только GET при сетевых ошибках и 502/503/504. Ошибки бронирования после готовности остаются ошибками теста; POST не повторяется автоматически. Пять регрессионных проверок выполняются командой `python3 -m unittest discover -s scripts -p 'test_*.py'`.
