# Hotel Service

Каталог отелей и номеров, распределение занятости и статистика. Сервис самостоятельно проверяет JWT, работает с собственной H2 и регистрируется в Eureka под именем `hotel-service`.

## Запуск и тестирование

Из корня репозитория:

```bash
./scripts/init-env.sh
set -a
. ./.env
set +a
./mvnw -pl hotel-service -am package
java -jar hotel-service/target/hotel-service-1.0.0.jar
```

По умолчанию HTTP-порт — `8082`. Переменные: `HOTEL_PORT`, обязательный `JWT_SECRET` (тот же секрет, что у Booking и Gateway), `EUREKA_URL` (по умолчанию `http://localhost:8761/eureka/`), `SEED_DATA=true`. В `.env` секрет генерируется скриптом. База in-memory: при перезапуске данные сбрасываются.

```bash
./mvnw -pl hotel-service -am test
```

Тесты поднимают Spring, H2 и MockMvc без внешних сервисов. Покрываются параллельные выделения, повторная доставка, равномерность распределения, отмена до подтверждения, пересечения дат, фильтры, статистика, CRUD и границы доступа.

Swagger UI: `http://localhost:8082/swagger-ui/index.html`; OpenAPI: `/v3/api-docs`; состояние: `/actuator/health`.

## Публичное API

В запросах передаётся `Authorization: Bearer <token>`. Чтение разрешено `USER` и `ADMIN`; изменения каталога и статистика — `ADMIN`. Объекты и коллекции возвращаются в JSON; коллекции используют Spring Page (`content`, `totalElements`, `totalPages`, `number`, `size`). Нумерация страниц начинается с нуля, размер по умолчанию 20, максимум 100.

| Метод и маршрут | Назначение |
| --- | --- |
| `GET /api/hotels` | Каталог; фильтры `name` (подстрока), `city` (точное совпадение без учёта регистра); `page`, `size`, `sort` |
| `GET /api/hotels/{id}` | Отель |
| `POST /api/hotels` | Создать отель, ответ 201 |
| `PUT /api/hotels/{id}` | Обновить отель |
| `DELETE /api/hotels/{id}` | Удалить отель с номерами, ответ 204; история бронирований запрещает удаление |
| `GET /api/hotels/{id}/statistics` | Статистика за обязательный интервал `startDate`, `endDate` |
| `GET /api/rooms` | Номера с фильтрами `hotelId`, `startDate`, `endDate`, `available`, `minCapacity`, `minPrice`, `maxPrice`; пагинация и сортировка |
| `GET /api/rooms/recommend` | Свободные номера на обязательные `startDate`, `endDate`; фильтры `hotelId`, `minCapacity`, `minPrice`, `maxPrice`; порядок всегда `timesBooked ASC, id ASC` |
| `GET /api/rooms/{id}` | Номер |
| `POST /api/rooms` | Создать номер, ответ 201 |
| `PUT /api/rooms/{id}` | Обновить номер; перемещение между отелями запрещено |
| `DELETE /api/rooms/{id}` | Удалить номер без истории, ответ 204 |

Пример отеля:

```json
{"name":"Невский","address":"Невский проспект, 15","city":"Санкт-Петербург"}
```

Пример номера:

```json
{"hotelId":1,"number":"104","available":true,"pricePerNight":4500.00,"capacity":2}
```

Ответ номера дополнительно содержит `id` и `timesBooked`. Допустимые поля сортировки отелей: `id`, `name`, `city`, `address`; номеров: `id`, `number`, `timesBooked`, `pricePerNight`, `capacity`. Пример: `sort=pricePerNight,desc`.

В обычном списке `available=true` по умолчанию. Без дат проверяется только операционная доступность; с датами исключаются занятые номера. Даты задаются вместе. `available=false` позволяет просмотреть выведенные из эксплуатации номера; рекомендации всегда включают только операционно доступные.

## Внутренний протокол

Эти запросы доступны только с отдельной ролью `INTERNAL` и закрыты на Gateway. Роль не выдаётся при регистрации пользователя.

| Метод и маршрут | Назначение |
| --- | --- |
| `POST /api/rooms/allocate` | Атомарно выбрать и занять номер, ответ `{"roomId":1}` |
| `POST /api/rooms/{id}/confirm-availability` | Занять конкретный номер; `autoSelect=false`, идентификатор в теле должен совпадать с URL |
| `POST /api/rooms/release` | Идемпотентная компенсация, 204; `roomId` может быть `null` |
| `POST /api/rooms/{id}/release` | Компенсация для известного номера, 204 |

Тело выделения:

```json
{
  "bookingId":"6739b355-1bee-4885-b1bb-d63db065c970",
  "hotelId":1,
  "roomId":null,
  "autoSelect":true,
  "startDate":"2030-06-01",
  "endDate":"2030-06-04"
}
```

При `autoSelect=true` поле `roomId` игнорируется. При явном выборе оно обязательно. `startDate` не раньше текущей даты; `endDate` строго позже. Повтор с тем же `bookingId` и параметрами возвращает прежний номер, не изменяя счётчик. Другой набор параметров с тем же идентификатором возвращает 409.

Тело компенсации:

```json
{"bookingId":"6739b355-1bee-4885-b1bb-d63db065c970","hotelId":1,"roomId":null}
```

Отмена неизвестного запроса создаёт запись `RELEASED`. Любое запоздавшее подтверждение с этим идентификатором получает 409, поэтому тайм-аут и переупорядочивание сетевых запросов не восстанавливают отменённую бронь.

## Алгоритм и схема данных

Все выделения, компенсации и изменения каталога одного отеля сериализуются пессимистической блокировкой строки `hotels` внутри локальной транзакции. После получения блокировки проверяются идемпотентность, операционная доступность и пересечения дат. Автоподбор сортирует подходящие номера по `times_booked`, затем `id`, и выбирает первый свободный. Выделение и увеличение счётчика фиксируются в одной транзакции. Счётчик означает число успешно выделенных слотов за всё время, включая последующие отмены: компенсация освобождает даты, но не уменьшает счётчик.

Интервалы полуоткрытые: `[start_date, end_date)`. Выезд и следующий заезд в один день допустимы. Пересечение существует при `existing.start_date < requested.end_date AND existing.end_date > requested.start_date`.

| Таблица | Основные поля и ограничения |
| --- | --- |
| `hotels` | `id`, `name`, `address`, `city`; индекс по городу |
| `rooms` | `id`, `hotel_id` FK, `number`, `available`, `times_booked`, `price_per_night`, `capacity`; уникальные `(hotel_id,number)`; индекс `(hotel_id,available,times_booked,id)` |
| `room_reservations` | `booking_id` UUID PK, `hotel_id` FK, nullable `room_id` FK, `start_date`, `end_date`, `status` (`ACTIVE`/`RELEASED`), `auto_select`, `created_at`; индексы пересечений `(room_id,status,start_date,end_date)` и `(hotel_id,status)` |

`room_reservations` — локальная проекция занятости для Booking Service. Запись компенсации, пришедшей первой, может не иметь номера и дат. Строки истории сохраняются; удаление связанных отелей/номеров отклоняется с 409. Для вывода номера из эксплуатации обновите `available=false`.

Статистика обрезает активные интервалы границами запрошенного периода. `bookedNights` — сумма занятых ночей; `roomNights` — число всех номеров × длительность периода; `occupancyPercent` — их отношение в процентах, округлённое до двух знаков. `operationalRooms` отдельно показывает доступные номера, `totalBookings` — накопленный счётчик за всё время. Для каждого номера возвращаются его занятые ночи и процент занятости. Отменённые интервалы не включаются.

Демо-данные: отель 1 «Невский», номера 1–3; отель 2 «Арбат», номера 4–5, причём номер 5 выведен из эксплуатации. Все счётчики изначально нулевые. Это позволяет воспроизвести порядок рекомендаций, равномерный подбор и фильтрацию.

## Ошибки и эксплуатационные ограничения

Ошибки используют общий `ErrorDTO`: `timestamp`, `status`, `code`, `message`, `path`, `traceId`, `details`. Основные коды: `NO_AVAILABILITY`, `IDEMPOTENCY_CONFLICT`, `RESERVATION_RELEASED` (409), `INVALID_DATES` (400), `ROOM_NOT_FOUND`/`HOTEL_NOT_FOUND` (404), 401 без корректного токена, 403 при недостаточной роли. `X-Trace-Id` проходит через сервис; операции выделения и отмены дополнительно логируют `bookingId`.

Блокировка действует в пределах общей базы данных. В этом учебном варианте используется один экземпляр Hotel Service со своей H2; для нескольких экземпляров нужна общая постоянная БД. Самостоятельный перезапуск сервиса сбрасывает in-memory историю; запускайте демонстрационный стек согласованно. Автоматическое удаление истории/временных блокировок не используется: освобождением управляет сага Booking Service.
